# Pipeline rebuild

The research pipeline (`pipeline/`) is rebuilt as a series of ten spikes so that one loop runs every claim, failed runs leave a machine-readable finding instead of a half-written claim, Analyst and Evaluator disagreements are settled by a rule, a weak verdict is restated automatically, published claims are rechecked on a schedule without going dark, and the `dr` command set shrinks to five commands a person can run from the docs. Each spike deletes the path it replaces in the same commit. The beta.7 pipeline fixes RE-AD to RE-AK (Evaluator grades the claim through Published fields survive the pipeline) are carried across by moved code and kept tests, listed in § Must preserve.

Status: approved by Brandon 2026-10-14 with every Q-B default; Phase 3 in progress (one spike at a time, run order in § Phase 3 run procedure)

Inputs: the interview note `handoff/2026-10-13-pipeline-improvement-interview.md` (Brandon's framing, answers Q1 to Q11, the run decisions) and the Phase 1 facts maps and synthesis in `docs/plans/pipeline-rebuild-map/` (`00-synthesis.md`, `orchestrator-loop.md`, `persistence-sidecar.md`, `researcher.md`, `ingestor.md`, `analyst-auditor.md`, `cli-review.md`, `tests.md`, `docs.md`, `beta7-fixes.md`). ## Goals and rules

Brandon's ranked goals (interview Q1):

1. Operator load: normal runs follow clear rules and ask Brandon nothing mid-run; flaws go to a findings file; runs restart or are abandoned by rule.
2. Output trust: the verdict on a claim rests on sources a person can check in one place.
3. Code legibility: one loop, one writer, about five commands; structure work only where it blocks the first two.

Immediate goals the spikes serve (interview framing): home-page claim cards on technology impacts (§ Card candidates); continuously updated sources and claims behind the Responsible AI chatbots page; a way to prove or dispute an ad hoc claim.

Premise (Brandon, Q6 correction): a person signs off on every claim. The pipeline's job is to make that sign-off easy, never to replace it. Nothing in this plan frames trust as a bar that lets review be skipped.

## End state

What is true after SP9 (Findings replay) lands.

### The loop and the writer

- `pipeline/loop/` holds the one run: research, ingest, analyse, evaluate, tie-break, restate. It takes a `ClaimSpec` (sentence, entity ref, criterion slug or none, topics, grading rule or none) and a `VerifyConfig`, returns a `VerificationResult`, and imports no writer; its public entries are `run` (the full run) and `rerun` (one agent over stored sources, same semaphore and retry; SP1 (One loop, one writer)), with `StepError` in `pipeline/loop/errors.py` and the step helpers tests call by public name (SP1's goal lists them). This is what Brandon's "one loop with a persist flag" means here: the switch between a dry run and a write is whether the command calls the writer, not a flag inside the loop, so an import-level test can prove `dr draft --dry-run` cannot write.
- `pipeline/orchestrator/persistence.py` is the one writer. Its write function runs in one order on every path: `mark_forced_rewrite` when an existing draft is replaced, then the cited source files through `persist_sources(result, repo_root, url_index)` (today a write method on `VerificationResult`, `pipeline.py:184-206`; SP1 (One loop, one writer) moves it into the writer so the result class carries no write), then the claim, then the full sidecar, whose `sub_questions` block the writer builds (`build_sub_questions_block`, today `pipeline.py:650-675`). The operator-field keep rules (`_write_claim_file`, `persistence.py:464-624`) are untouched and called from the writer. The level fit (`fit_verdict_to_written_pool`, `persistence.py:354-447`) is a pure function over the in-memory result; it stays in `persistence.py` until SP6b (Source pool rules) moves the function and its one real call together into `pipeline/loop/fit.py`. The moved cited filter already imports it from `persistence.py` as a predicate (`pipeline.py:1587, 1600`), which is allowed: a loop module may import `persistence.py` readers and pure helpers, never `_write_*`, `persist_sources` or `mark_forced_rewrite` (the import-level test checks those names); moving the fit file in SP1 would make `persistence.py` import the loop package while the loop imports `persistence.py`, a circular import. The fit is called once on the real verdict after the cited filter has fixed the final source ids (by the writer until SP6b, inside the loop before the Evaluator from SP6b on), and its note always lands in `pipeline_run.level_clamp` (beta7-fixes map hazard H4, owned by SP1 and SP6b).
- `pipeline/orchestrator/` keeps `cli.py` (five commands), `persistence.py`, `review.py`, `entity_resolution.py`; `pipeline.py` and `checkpoints.py` are deleted. Leaf packages (`researcher/`, `ingestor/`, `analyst/`, `auditor/`, `linter/`, `common/`) keep their files (one import line, `researcher/decomposed.py:20`, is re-pointed at `loop.errors.StepError` in SP1 (One loop, one writer)); the tie-breaker and restater are agent packages under `pipeline/loop/` using the `instructions.md` layout `pipeline/tests/test_instructions.py:38-59` requires.
- One sidecar shape (`<claim>.audit.yaml`): keys are only added, never renamed, and every added key is declared in `src/content.config.ts` in the same commit.

### The claim record

- Every claim stores the sentence the loop re-runs in frontmatter key `statement` (name chosen here; `claim` is a legacy fallback at `cli.py:1142, 1414` and is not in `CANONICAL_CLAIM_KEYS`, `pipeline/linter/checks.py:30-36`). `title` equals `statement` for sentence claims; the Evaluator grades `statement`. `statement` is optional in the schema; a claim without one (the 8 claims on disk until their next run) is re-run from `title`.
- A criterion-backed claim is `dr draft --criterion <slug> --entity <ref>`: the criterion's text is rendered once with the entity name and stored as `statement`; `criteria_slug` points at `research/templates.yaml`, which stays the criterion registry (Q-B1 (criterion registry) default) and the publish gate (`review.py:128-134`, `checks.py:95-123`). The `vocabulary` slots and the "one of (...)" hint leave the pipeline (`pipeline/common/templates.py` stops reading the key), but the `vocabulary` key itself stays in `research/templates.yaml` as a site-only key: the home page bolds its terms (`src/pages/index.astro:16-20, 46-47`) and the Responsible AI matrix's ownership row is validated against it at build time (`src/content/resources/responsible-ai.md:241-246`, `src/lib/matrixCheck.ts:121-130`, `src/lib/matrixLookups.ts:45`, run by `src/pages/resources/[...slug].astro:48`), through the unchanged criteria schema (`src/content.config.ts:281`). `grading_rule` is a per-criterion field that reaches Analyst and Evaluator in place of `notes` (the RE-AL (Source pool and coverage quality) decision, `docs/v1.0.0-roadmap.md:338`).
- An ad hoc claim is `dr draft --entity <ref> "<sentence>"` or `dr draft --subject <slug> "<sentence>"`; it has no `criteria_slug`, and `dr review --approve` refuses a claim without one (`review.py:120-126`; lint `published-without-criterion`, `checks.py:95-123`). Before sign-off a criterion is attached with `dr draft --claim <ref> --criterion <new-slug>` (Q-B13 (publishing an ad hoc claim) default, built in SP6a (One claim path)): the command appends a criterion entry to `research/templates.yaml` built from the stored claim (`text` is `statement` with the first match of the entity name or an alias replaced by the entity type's placeholder, else `statement` verbatim, which is how the subject criteria on disk read, `research/templates.yaml:130-134`; `entity_type` from the entity ref; `subjects: [<ref>]` for a subject; `topics` copied; `core: false`), writes `criteria_slug`, runs no loop and moves no file. The five card drafts and every restatement pick go through it (§ Phase 3 run procedure, Phase 4 close).
- Claim path (the claim id and the site URL are the file path, frozen by interview Q10): `--criterion` writes `<entity-dir>/<criteria_slug>.md` (today's onboard stem, `pipeline.py:2713-2716`; the eight published claims on disk are at `research/claims/*/renewable-energy-hosting.md` and under `research/claims/subjects/`); `--claim` and `--rerun` write to the claim's existing path even when `statement` differs from the stem; an ad hoc claim writes `<entity-dir>/<slugify(statement)>.md` (today's claim-draft stem, `pipeline.py:1805-1812`, with the analyst's title replaced by the statement); `--restates` is a new claim at its own ad hoc path; attaching a criterion never moves a file (the `<criteria_slug>.md` stem applies only to claims created by `--criterion`). `<entity-dir>` is `_claim_dir_for` (`persistence.py:313-328`, flat for products, type-prefixed for subjects). A recheck's pending draft uses the same stem under the pending location and moves over the live path at promotion.

### Entities

Products and subjects are the only entity types the pipeline writes claims for: from SP8 (Companies out) on, every `dr draft` mode whose entity resolves to `companies/` (`--entity`, `--criterion`, `--claim` on an existing company claim, `--restates` of one) exits with one usage error before any model call. Product files are hand-written; `dr draft --subject <slug>` writes a minimal subject record (`research/entities/subjects/<slug>.md`: name, description from the sentence) when none exists. Onboarding, light research, the entity verifier and the enricher are deleted (Q-B6 (entity files) default). Company files stay on disk as read-only parent records feeding first-party matching (`entity_identity_for`, `pipeline/orchestrator/entity_resolution.py:63-75`); the five active company criteria are deactivated (Q-B3 (companies) default).

### The review packet

`dr review` renders, per draft, the four parts below in Brandon's ranked order (Q6). Only part 1 and the header facts are promised on one screen (the interview note `:26` ranks part 1 alone as "on one screen"): they print last, directly above the key prompt, within 40 lines (the bound the SP4 (Review packet) test pins; part 2 alone can run to 8 sources with several quotes each and part 4 to 32 rejected candidates, so the whole packet cannot fit). Parts 2 to 4 print above them, in ranked order, for scroll-back; the `v` key opens the whole packet in `$PAGER` the way `p` opens the claim today (`pipeline/orchestrator/review_queue.py:222-225`), and `dr review --format text --claim <ref> | less` gives the same outside the walkthrough.

1. The verdict chain: original sentence (`statement`), restated candidates with their expected verdicts, Analyst, Evaluator, tie-breaker, each with a one-line reason; `pipeline_verdict` and `rule_applied`.
2. Every key quote beside its archived passage with the automated check's pass or fail (`sources_consulted[].quotes[] {text, found, checked_against, passage}`; `passage` is the matched sentence plus a bounded window of the normalised page text around it, written by the ingest check that today returns only the dropped quotes (`pipeline/ingestor/validation.py:106-128`); a not-found quote carries the reason instead; `not-rechecked` for cached sources). When the source has an `archived_url`, the packet also prints a text-fragment link (`<archived_url>#:~:text=<quote>`) so the operator can open the passage in the archive copy.
3. Source independence at a glance: publisher, kind, independence label, the "Off-entity:" and "Entity match:" reasons, and `sources_consulted[].shared_with: [<source-id>...]` naming the other consulted sources with the same canonical publisher host (`pipeline/common/canonical_url.py`) or, from SP6b (Source pool rules) on, the same newswire origin. Detecting two publishers reporting one study (the C7 BBC case in § Card candidates) is not in this series; it is a follow-up row (§ Questions for Brandon, after Q-B12).
4. What the run searched for and rejected: queries including the counter-evidence sub-question, rejected candidates with the scorer's reason (`research.rejected[] {url, score, reason}`).

The existing header facts (source counts, tags, takeaway, seo_title, a pending recheck's previous verdict and date) print with part 1, above the prompt.

### The findings file

One YAML record per finding at `research/findings/<yyyy>/<run-id>.yaml` (inside `research/` per the AGENTS.md:72 boundary rule; outside every site collection loader, which read `claims/`, `entities/` and `sources/` only). The directory is tracked in git (§ Run rules, "Tracked research output"); `dr lint` skips it; spike commits and scheduled runs stage the findings they produce.

```yaml
run_id: a06d7a7e3fea4120b0d1f879bec059e1
date: 2026-10-20
command: dr draft
claim_spec:
  statement: "In 2024, US data centers got more of their electricity from natural gas than from all renewable sources combined."
  entity: subjects/us-data-centers
  criteria_slug: null
  topics: [environmental-impact]
  grading_rule: null
claim_ref: null            # set when a claim file exists for this run
config: {max_sources: 8, candidate_pool_size: 32, max_initial_queries: 7, search_backend: tavily, research_origins: [tavily, arxiv], model: greenpt:gpt-oss-120b}
models_used: {researcher: greenpt:gpt-oss-120b, ingestor: infomaniak:ministral-3-14b}
step: ingest               # research | ingest | analyse | evaluate | tiebreak | restate | write
rule: flaw-retry           # flaw-retry | transport-retry | config-fatal | half-claim | tiebreaker | replay
error: {error_type: insufficient_sources, message: "3 usable sources, 4 needed"}
attempts: 2
outcome: abandoned         # recovered | abandoned | split | half-claim | partial (restater failed after a valid verdict; the claim was written without a restatement block)

```

`dr findings` lists open records; `--summary` counts by step, rule and outcome; `--close` records a hand triage; `--replay` (SP9 (Findings replay)) re-runs `claim_spec` and `config` through the loop and closes the finding or records a new one.

### SP5. Recheck

**Goal.** `dr recheck --due` re-runs every due claim without stopping (due: `next_recheck_due` has passed or, when the claim has none, `as_of` plus `recheck_cadence_days` has passed, § Run rules; no claim on disk carries `next_recheck_due`, so the first batch is selected by `as_of`); `dr recheck --due --dry-run` lists the due claims with their due dates and calls no model: each claim's failure becomes a finding and the batch continues, one summary line per claim, one LLM semaphore.
