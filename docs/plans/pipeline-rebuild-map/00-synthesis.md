## 1. Recommendation

**APP-1 (strangler) with APP-2's shape.** Build `pipeline/loop/` by *moving* the loop that already exists, not by writing a new one, and keep `pipeline/orchestrator/persistence.py` as the single writer.

What the evidence settled:

- `verify_claim` (`pipeline/orchestrator/pipeline.py:345-553`) is already the one in-memory loop: it never writes a file, and `onboard_entity` (`:2723-2729`) and `claim_refresh` (`cli.py:1167-1173`) already call it. Only `research_claim` (`:1619-1866`, `dr claim-draft`) is a true copy. The duplication Brandon wants gone is the copy plus the two four-branch write blocks (`pipeline.py:2746-2967`, `cli.py:1213-1333`) and the inlined writes in `research_claim`. (APP-2's argument 1, confirmed by the orchestrator map § 2.)
- The beta.7 fixes RE-AD to RE-AK live mostly in leaf modules (`wayback.py`, `validation.py`, `arxiv_affiliation.py`, `source_classification.py`, `citations.py`, the instruction files) and in `persistence.py` (the keep rules, 116 tests in `test_audit_trail.py`). A loop package that is a set of `git mv` renames of the orchestrator helpers, plus one writer function in `persistence.py`, keeps all of that by import change. (Both skeptics' fixes converge here: "move `_ingest_one` ... as file moves", "keep `_write_claim_file` as the one write path".)
- The skeptics' blocking findings were against the *order* and the *content* of the spikes, not against the strangler: SP1 cannot delete `verify_claim` while onboard and refresh still call it (migration skeptic); SP5 cannot precede SP6 (all three skeptics); SP6 has no criterion registry and SP5 has no file model (end-system and operator skeptics). Each is answered below.

What changed from APP-1 as the advocate proposed it:

1. **No persist flag inside the loop.** The loop returns a result and never imports a writer; `dr draft` calls the writer, `dr draft --dry-run` does not. Probe safety is pinned twice: an import-level test (`pipeline/loop/` references none of `_write_source_files`, `_write_claim_file`, `_write_audit_sidecar`, `_write_entity_file`, `mark_forced_rewrite`, `set_claim_status`) and a zero-write test on scripted inputs that also asserts `_save_and_check` (`pipeline/ingestor/tools/wayback.py:376-390`) and the `url_index` write-back (`pipeline.py:198-203`) are never reached. This avoids the risk `docs/architecture/open-issues.md:52-62` named rather than mitigating it.
2. **SP1 moves code and writes one writer; it changes no verdict behaviour.** Its proof is a differential test: old `research_claim` versus the new loop plus writer on the same scripted inputs, run before the old function is deleted in the same commit. The nine divergences the map lists (§ 2.5) are decided once in SP1 (§ 8 below), which is a behaviour change only where the three copies already disagreed.
3. **SP1 routes onboard and claim-refresh through the loop and the writer** (deleting both write blocks) instead of leaving them on `verify_claim`. There is then one loop and one outcome policy from the first commit; the "four loops" window and the "two outcome conventions" window both close.
4. **SP6 (one claim path) runs second**, before SP2 (rules and findings). All three immediate goals (home-page cards, Responsible AI page sources, ad hoc claims) route through SP6; and SP6 deletes `onboard_entity` with its four entity gates, so SP2 then has only the two loop checkpoints to retire instead of converting onboard's gates into rules that SP6 deletes a spike later.
5. **The loop's input is decided in SP1** as a plain record (sentence, entity ref, criterion id or none, topics, grading rule or none; call it `ClaimSpec`, name is the plan's) with a thin template adapter, so SP6 deletes the adapter instead of rebuilding the input, and the Evaluator's graded-statement rule (RE-AD) is rewritten once (SP6), not three times.
6. **Failure writes nothing.** From SP1 the writer runs only on success: no placeholder `blocked` claims, no orphan source files, no overwrite of a published claim by a failed rerun. The finding (SP2) is the only record of a failed run. `blocked` stays in the site enum until SP7.
7. **Prerequisites before SP1:** a pytest job in CI (the spikes delete code that only the local hook would catch), and Brandon commits or moves the 10 untracked `research/sources/` files (the hook builds the whole tree, so they can block every spike commit).

End state after SP9: `pipeline/loop/` (the run: research, ingest, analyse, evaluate, tie-break, restate; returns a result), `pipeline/orchestrator/` (`cli.py` with five commands, `persistence.py` as the one writer, `review.py`, `entity_resolution.py`), the leaf packages unchanged, `pipeline.py` and `checkpoints.py` deleted. Commands: `dr draft` (with `--dry-run`, `--criterion`, `--subject`, `--rerun analyst|evaluator`, `--force`), `dr recheck` (`--due`, `--claim`, `--sources`), `dr review` (queue walkthrough rendering the packet; `--claim --approve|--archive`), `dr findings` (`--summary`, `--replay`), `dr lint` (`--prune`). One sidecar shape (`.audit.yaml`, additive keys, declared in `src/content.config.ts` as they are added). One claim record: a stored sentence plus an optional `criteria_slug` pointing at `research/templates.yaml`, which stays the criterion registry (D1). Products and subjects are the entity types the pipeline writes claims for; company files stay as read-only parent records unless Brandon chooses full removal (D3).

## 6. Decisions only Brandon can make

Keep to these six. Everything else has a default in § 7 that he can override at the stop.

**D1. Criterion registry.** Does `research/templates.yaml` stay the one criterion record (site criteria pages, comparison matrix, lint `broken-criteria-slug`, publish gate) with each claim storing its own sentence plus a `criteria_slug` pointing at it, or does a new `research/criteria/` record replace it for the pipeline, lint, the criteria pages and the matrix in the same spike?

Recommended: (a). It is the smallest change that gives one claim record and keeps the site's URLs and matrix untouched.

**D2. Pending recheck carrier, and where a scheduled run commits.** Where does a recheck's result live while the old published claim stays live?
Why only Brandon: it decides the file layout under `research/`, what the site ignores, and whether a scheduled job writes to his checkout, a branch, or a PR (the project memory says no PRs before beta).
Options: (a) a pending location outside the site's claims loader (for example `research/pending/<entity-dir>/<slug>.md` plus sidecar) that `dr review` promotes by moving the files over the live claim and writing the refresh snapshot and correction; (b) today's model: overwrite in place with the `refresh` block, accepting the page goes dark until sign-off; (c) a branch per scheduled run. Scheduled runs: Brandon's checkout by hand first (Q7), then a GitHub Actions job writing to a branch that Brandon fetches and reviews locally.
Recommended: (a) with the Actions branch for the scheduled phase.

**D3. Companies.** Full removal of the company entity type (schema enum, `parent_company`, company pages, seven company templates, product files absorbing parent names) or company files stay as read-only parent records with the five active company criteria deactivated?
Why only Brandon: full removal deletes public pages and changes product entity files; the reduced form is a content and docs change.
Options: (a) keep as parent records, deactivate company criteria, SP8 shrinks to docs and `templates.yaml`; (b) full type removal in SP8.
Recommended: (a). Product `parent_company` refs feed first-party matching (`entity_resolution.py:63-75`), reader value of removal is low, and Q8 ranked it last.

**D4. Retry policy.** The value of N for flaws and for transport errors, and whether a retry that succeeds still records a finding.
Why only Brandon: it sets model spend per failed run and how much variance is allowed to rescue a run.
Options: N(flaw) in {0, 1, 2}; N(transport) in {1, 2, 3}; recovered retries recorded or not.
Recommended: N(flaw) = 1, N(transport) = 2 (today's `_NULL_BODY_RETRIES`), recovered retries always recorded.

**D5. Tie-breaker.** Is the third pass blind (same bundle as the Evaluator, never shown the two prior opinions) or a judge that sees both; and the "weaker verdict" ordering for a three-way split.
Why only Brandon: it is the output-trust rule for every disagreeing claim; the interview left "weaker" undefined and `unverified`/`not-applicable` are off the polarity scale (`compare.py:9-16`).
Options: blind or judge; ordering (recommended) not-applicable < unverified < mixed < mostly-true/mostly-false < true/false, the draft takes the weakest side's verdict and that side's confidence.
Recommended: blind, with that ordering. Blind keeps the independence the Evaluator tests enforce; the frontier model is spent only on the hard case (AGENTS.md:17).

**D6. Entity files after SP6.** Does the pipeline still create or enrich entity files?
Why only Brandon: the default retires RE-AJ (Entity enrich refuses to guess), a fix he approved in beta.7, and makes product entity files a hand-written input.
Options: (a) products hand-written; `dr draft --subject` writes a minimal subject record when missing; no light research, verifier or enricher; `claim-draft -`, `onboard` and `entity-enrich` deleted; RE-AJ marked retired; (b) keep `dr entity-enrich` as a sixth command carrying RE-AJ.
Recommended: (a). Nine product files exist and are edited by hand already; onboarding's light research spends two model calls to find a homepage (researcher map H13).
